## 1. Audit Summary (A.1 – A.4)

### A.1 — Cold Start & Entry Paths
- **Gap 1 (`MainActivity.onStart` pre-unlock hearth calls):** `MainActivity.onStart()` previously ran `HearthWatchScheduler.refreshNow(this)` and `chatViewModel.assistantService.value?.retryConnectionNow()` before `AppLock` unlock (and before `LifecycleEventObserver` `ON_START` updated `AppLock.onForeground()`), causing `HearthWatchWorker` (`custosCards`, `listSessions`, `events`) and `AssistantService.onCreate()` (`maybeRestoreHearthChat` / `initConnectionMonitoring`) to contact the hearth while locked.
  - **Fix:** `MainActivity.onStart()` now calls `AppLock.onForeground()` first and guards hearth refresh and connection retry behind `AppLock.policy.canReachHearth()`, with an unlock-triggered `LaunchedEffect` inside the unlocked branch (`MainActivity.kt:234-244`, `346-351`).
- **Gap 2 (`lararium://pair` deep link pre-unlock dialog & pairing):** `MainActivity` previously invoked `handlePairingIntent(intent)` synchronously in `onCreate()` and `onNewIntent()`, displaying a pairing `AlertDialog` over `LockScreen` and executing `LarariumClient.health()`, `SecureKeyManager.setHearthEndpoint()`, and `DevicePairingController.autoRegister()` without unlocking `AppLock` or passing `authGate`.
  - **Fix:** `lararium://pair` intents are queued into `pendingPairingUri` via `enqueuePairingIntent(intent)` and only presented inside the unlocked Compose branch, with `connectPairedEndpoint()` gated by `authGate(..., verb = ScaryVerb.HEARTH_PAIR_WRITE, replacingExistingSecret = replacingExisting)` (`MainActivity.kt:132-202`, `353-357`).
- **Gap 3 (`DevicesActivity` / `lararium://device-pair` missing `AppLock` gate):** `DevicesActivity` (`android:exported="true"`) lacked `AppLock` foreground/background tracking, `LockScreen` gating, and `FLAG_SECURE`.
  - **Fix:** Added `FLAG_SECURE`, `AppLock.onForeground()` / `AppLock.onBackground()` observer, and `AppLock.isUnlockedState` `LockScreen` gate to `DevicesActivity` (`DevicesActivity.kt:23-83`).
- **Gap 4 (`CompactAssistantActivity` & `AssistantService` overlay entry):** Launching the assistant overlay via Quick Settings tile, shortcut, or voice interaction bound `AssistantService` and allowed hearth probes/queries while locked.
  - **Fix:** `CompactAssistantActivity` now extends `FragmentActivity`, tracks `AppLock` foreground/background state, and gates UI + service binding behind `LockScreen` (`CompactAssistantUI.kt:59-160`). `AssistantService` guards `processQueryInternal()`, `maybeRestoreHearthChat()`, and `isMonitoringEligible()` behind `AppLock.policy.canReachHearth()` (`AssistantService.kt:703-708`, `1088`, `1268`).

### A.2 — Scary Verbs & Vault/Keystore Writes
- **Already Gated:**
  - Connector add/edit + `SECRET_TEXT` / `SECRET_MAP` vault writes: `ConnectorFormScreen.kt:134` (`submitForm` -> `authGate`).
  - Connector delete: `ConnectorsScreen.kt:195` (`handleDeleteConfirmed` -> `authGate(..., destructive = true)`).
  - Approval card resolve (approve/deny): `ApprovalsScreen.kt:83` (`resolveCard` -> `authGate`); notification actions route via `CardActionReceiver.kt:33` to `MainActivity` review UI.
  - Device rails re-pair & forget: `DevicesScreen.kt:301`, `431` (`authGate(..., destructive = true)`).
  - Payment-shaped flows: **N/A v1** (no payment/wallet/purchase surface exists in v1).
- **Gaps Found & Fixed:**
  1. **`SettingsScreen.kt` `PairHearthDialog.doPair()` (`SettingsScreen.kt:1319-1409`):** Both `pair1_` code redemption and `lararium://pair` / URL+token pairing wrote to `SecureKeyManager.setHearthEndpoint()` without `authGate`. Wrapped both paths in `authGate(context, verb = ScaryVerb.HEARTH_PAIR_WRITE, replacingExistingSecret = app.secureKeyManager.hasHearthEndpoint())`.
  2. **`SettingsScreen.kt` Hearth Unpair (`SettingsScreen.kt:253-270`):** Cleared `SecureKeyManager.clearHearthEndpoint()` without `authGate`. Wrapped in `authGate(context, verb = ScaryVerb.HEARTH_UNPAIR_CLEAR)` (`destructive = true`).
  3. **`MainActivity.kt` `connectPairedEndpoint()` (`MainActivity.kt:176-202`):** Deep-link pairing wrote hearth endpoint and auto-registered device rails without `authGate`. Wrapped in `authGate(context, verb = ScaryVerb.HEARTH_PAIR_WRITE, replacingExistingSecret = replacingExisting)`.
  4. **`DevicePairingScreen.kt` `submitPairing()` (`DevicePairingScreen.kt:82-115`):** Wrote device rails credentials (`DevicePairingStore.saveEndpoint` -> `SecureKeyManager.setDeviceToken`/`setDeviceId`/`setDeviceBaseUrl`) without `authGate`. Wrapped in `authGate(context, verb = ScaryVerb.DEVICE_RAILS_PAIR_WRITE, replacingExistingSecret = replacingExisting)`.
  5. **`ConnectorsScreen.kt` `handleReauth` (`ConnectorsScreen.kt:172-195`):** Re-authenticated connectors via `ConnectorsClient.reauthConnector()` without `authGate`. Wrapped in `authGate(context, reasonTitle = "Re-authenticate Connector", destructive = false)`.
  6. **`ActionConfirmActivity.kt` `onApprove` (`ActionConfirmActivity.kt:42-90`):** Upgraded `ActionConfirmActivity` to `FragmentActivity`, applied `FLAG_SECURE`, and wrapped `onApprove` in `authGate(context, verb = ScaryVerb.DEVICE_ACTION_APPROVE)`.

### A.3 — Backup Semantics & Pair Token Custody
- **Keystore Custody:** `SecureKeyManager` wraps all secrets (`hearth_endpoint`, `pairing_code`, `device_token`, `device_id`, `device_base_url`) with AES-256-GCM under AndroidKeyStore alias `assistant_encryption_key` (`SecureKeyManager.kt:23-136`). AndroidKeyStore keys are non-exportable and never leave the device; any backup/restore of `assistant_secure_prefs.xml` carries only ciphertext and fails closed (`null`) without the original hardware-backed key.
- **Gaps Found & Fixed:**
  1. **Leftover legacy plaintext purge (`SecureKeyManager.kt:215-243`, `297-325`, `347-373`, `397-423`):** Previously, if `assistant_secure_prefs` already contained an encrypted key, `getPairingCode()` / `getDeviceToken()` / `getDeviceId()` / `getDeviceBaseUrl()` returned early without purging a stale/blank key in `local_token` or `device_rails_plain`. Updated all four getters to always purge any leftover key in `plainPrefs`.
  2. **Pure JUnit test seam (`SecureKeyManager.kt:18-21`, `96-100`):** Added optional `secretKeyProvider: (() -> SecretKey)? = null` constructor parameter and `java.util.Base64` encoding so `SecureKeyManager` encryption, migration, and backup-restore behavior are directly unit-tested in `SecureKeyManagerTest` without new test dependencies.
  3. **`backup_rules.xml` (`app/src/main/res/xml/backup_rules.xml:1-9`):** Replaced placeholder comments with explicit `<exclude>` entries matching `full_backup_content.xml` and `data_extraction_rules.xml` (`local_token.xml`, `assistant_secure_prefs.xml`, `device_rails_secure.xml`, `device_rails_plain.xml`, `chat_history`, `hearth_watch.xml`).

### A.4 — Authenticator Policy & Fallback Behavior
- **Gaps Found & Fixed:**
  1. **API 26–29 `DEVICE_CREDENTIAL_ONLY` silent bypass (`BiometricPromptAuthenticator.kt:73-83`, `BiometricAuthPolicy.kt:64-78`):** `BiometricAuthPolicy.determineStrategy` returns `DEVICE_CREDENTIAL_ONLY` only on API 26–29 when `hasStrongBiometric == false && hasDeviceCredential == true`, yet `BiometricPromptAuthenticator` previously had `if (Build.VERSION.SDK_INT >= 30) ... else onResult(true)`, silently bypassing authentication on API 26–29 when only a PIN/pattern/password was enrolled. Fixed `BiometricAuthPolicy.allowedAuthenticatorsFor(DEVICE_CREDENTIAL_ONLY, sdkInt)` to use `BIOMETRIC_WEAK or DEVICE_CREDENTIAL` (`0x80FF`, supported by `androidx.biometric:1.1.0` on API 26–29) and launch `BiometricPrompt`.
  2. **API 26–29 `BIOMETRIC_STRONG_ONLY` credential fallback (`BiometricAuthPolicy.kt:80-99`, `BiometricPromptAuthenticator.kt:85-115`, `135-138`):** When both strong biometrics and device credentials are enrolled on API 26–29, `BIOMETRIC_STRONG_ONLY` now sets negative button text `"Use PIN"` and falls back to launching the device-credential prompt on `BiometricPrompt.ERROR_NEGATIVE_BUTTON`.
  3. **Silent `NO_HARDWARE_PASSTHROUGH` (`BiometricAuthPolicy.kt:101-109`, `BiometricPromptAuthenticator.kt:57-71`):** When neither biometrics nor device credentials are enrolled, `BiometricPromptAuthenticator` now logs a warning (`Log.w`) and shows a user-visible `Toast` (`BiometricAuthPolicy.NO_ENROLLMENT_WARNING`) before allowing passthrough, so fallback is never silent.
